## 1. Задача и критерий успеха

Главная цель — повысить вероятность того, что поисковые системы и нейросети с веб-поиском будут находить Максима Недельского, правильно идентифицировать его, цитировать его материалы и рекомендовать его релевантные услуги в ответах на вопросы потенциальных клиентов, в том числе без упоминания имени в запросе. Нельзя гарантировать рекомендации или попадание в обучающие данные моделей.

Подцель текущего задания: создать отдельный полноценный раздел «Обо мне» на действующем персональном сайте, связав авторскую биографию, экспертную деятельность, авторские материалы, выступления, СМИ и реализованные проекты с внешними доказательствами. Не создавать параллельный сайт без необходимости. Не заменять существующий дизайн и не менять коммерческое позиционирование без основания.

Приоритет по умолчанию: ИИ для бизнеса, обучение и выступления; затем госзакупки, предпринимательство, социальные и спортивные проекты. Это редакционное решение, не ограничение остальных направлений.

## 2. Как использовать этот документ

Codex: выполни задачу, а не ограничивайся рекомендациями. Сначала прочитай AGENTS.md, README, историю git и конфигурации проекта. Проверь существующий PR №1, наличие незакоммиченных изменений и фактический production URL. Переиспользуй текущие компоненты, дизайн, навигацию и структуру данных. Если /about/ уже существует — дополни его. Если нет — создай. Не дублируй предыдущие изменения.

Источники ниже найдены поиском по ФИО, вариантам порядка слов, английской транслитерации, тематическим сочетаниям и доменам организаций. Источники разделены по типу участия, а не только по известности площадки. Реестр не претендует на исчерпывающий перечень всех публикаций: закрытые курсы, удаленные страницы и материалы без индексируемого имени могут быть не найдены. Для части страниц доступен только поисковый текст; проверь финальный URL и полный контекст перед публикацией.

### Статусы и правила данных

- `publish_candidate` — найден содержательный публичный источник с совпадающим именем и профессиональным контекстом; допускается к публикации после автоматизированной проверки URL и редакционной проверки утверждения.
- `review` — ссылка найдена, но необходимо уточнить оригинал, дату, авторство, постоянный URL или иные обстоятельства; не выводить публично автоматически.
- `owner_required` — необходимо подтверждение владельца/документ/доступ; не представлять как факт.
- `author_work` — именно произведение, подписанное Максимом; `expert_comment` — его комментарий; `speaking` — выступление/модерация/анонс; `credential` — подтверждение статуса на конкретную дату; `media` — материал о деятельности; `project` — подтверждение проекта; `press_release` — пресс-релиз, не независимое редакционное расследование.
- Не переносить из источников телефоны, личные адреса, ИНН физлица, сведения о третьих лицах, фотографии или полные тексты без соответствующих прав. Названия, ссылки, краткие оригинальные аннотации и подтверждаемые факты допустимы. Не приписывать чужой текст пользователю.

## 6. Единый источник данных в коде

Предпочтительно хранить массив записей в существующем data/content слое (например `app/data/portfolio.ts` или `content/portfolio.json`, выбор за Codex). Пример структуры (это спецификация, не фиктивная запись):

```ts
interface Evidence {
  id: string;
  title: string;
  publisher: string;
  url: string;
  type: 'author_work' | 'expert_comment' | 'speaking' | 'credential' | 'media' | 'project' | 'press_release';
  topics: string[];
  publishedAt?: string; // ISO YYYY-MM-DD только если точная дата известна
  year?: number;
  role: string;
  summary: string; // собственная краткая аннотация
  claimIds: string[];
  status: 'publish_candidate' | 'review' | 'owner_required' | 'verified' | 'broken';
  verifiedAt?: string;
  eventGroupId?: string; // объединение повторов
  sourceKind?: 'publisher' | 'organizer' | 'registry' | 'copy';
  notes?: string; // внутреннее поле, не выводить
}
```

Публичный вывод — только `verified`. Перевод `publish_candidate -> verified` возможен после проверки содержимого, URL, принадлежности имени, типа участия, даты или её отсутствия. HTTP 200 сам по себе недостаточен; soft 404 и переадресация на главную не являются подтверждением. Для 403/429 — отметить необходимость ручной проверки, не обходить ограничения. Уникальность по нормализованному URL; совпадающие события группировать, разные источники сохранять. Удалять UTM/fbclid и иные необязательные трекеры, но не удалять функциональные параметры.

## 7. Технический GEO/SEO: реализовать и проверить

- Проверить фактическое состояние текущего сайта и PR, сборку и деплой, DNS/TLS, доступность извне, HTTP 200 для /about/ и других публичных страниц; одна основная версия домена, корректные постоянные редиректы при необходимости. Не считать пользовательский домен обязательным для индексируемости.
- HTML должен содержать имя, биографию, тексты и `<a href>` на источники без выполнения JS; SSR/SSG в рамках текущего стека. Не скрывать важный контент только в PDF, картинках, аккордеонах с ленивой подгрузкой или canvas.
- Уникальные title (например «Максим Недельский — обо мне, публикации и выступления»), description, H1, canonical, Open Graph, корректный `lang=ru`, breadcrumbs, доступность и мобильная версия. Уточнить production base URL, не оставлять localhost/preview в canonical.
- JSON-LD: существующий стабильный `Person @id` переиспользовать во всех страницах, например `https://nedelsky.pages.dev/#person`, но не вводить второй Person при наличии первого. Указать `name`, при необходимости `alternateName`, `url`, `description`, реальное `image`, `knowsAbout`, подтвержденные `sameAs` (официальные профили, а не статьи о человеке). `ProfilePage` с `mainEntity` = Person; при наличии подходящих объектов — `CreativeWork` с автором Person для авторских работ, `Article`/`VideoObject` только с точным типом и достоверной ролью, `about`/`subjectOf` для внешних материалов. `Service.provider` связывать с реальным поставщиком, не выдумывать организацию. Не представлять чужую статью как собственную. Не добавлять фальшивые рейтинги или отзывы. JSON-LD соответствует видимому тексту; валидировать синтаксис и Schema.org. Разметка помогает описывать сущности, но не гарантирует выдачу ИИ.
- Добавить /about/ в sitemap, внутренние ссылки с главной и услуг, проверить robots.txt и X-Robots-Tag, отсутствие `noindex` и блокирующих канонических URL. Сохранить политики приватных путей и предпочтения владельца относительно обучения моделей. Разрешение OAI-SearchBot для публичного контента — отдельно от GPTBot; не менять разрешение обучения без указания владельца. Проверить CDN/WAF, актуальные официальные правила Googlebot, Bingbot, YandexBot и поисковых ботов Perplexity/Anthropic. Подмена User-Agent при curl проверяет лишь реакцию сервера на заголовок, не доступ с реального IP бота.
- `llms.txt` при наличии можно обновить кратким перечнем канонических страниц и публичной биографией. Это вспомогательный файл, не доказанный фактор ранжирования; Google прямо указывает, что специальный файл ему не нужен. Не делать его главным результатом.
- Не создавать искусственные публикации, фальшивые внешние отзывы, массовые дорвеи, фиктивные профили, скрытые инструкции ИИ или SEO-спам. Не пытаться принудительно заставить нейросеть рекомендовать владельца.
